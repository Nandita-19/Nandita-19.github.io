AML Transaction Monitoring

A rules-driven pipeline for screening transaction behavior, with emphasis on structuring patterns and unusual transaction velocity.

PostgreSQLSQLApache AirflowData quality

Why this work matters

Transaction datasets often contain patterns that are difficult to spot through manual review. This independent project explores repeatable SQL checks that help surface transactions requiring further review; a rule hit is an investigative signal, not proof of wrongdoing.

My approach

  • Prepared a PostgreSQL-based environment to run repeatable transaction analysis.
  • Developed structuring checks and transaction velocity / volume logic with SQL.
  • Used an Airflow DAG to orchestrate monitoring checks, with emphasis on reproducibility and dependencies.
  • Organized the checks by detection category so additional rules can be added and tested independently.

Engineering choices and quality checks

Rule-focused SQL

Screen for transaction patterns using auditable query logic instead of presenting a rule hit as a confirmed financial crime.

Historical baselines

Compare recent transaction activity with longer windows to separate unusual volume from normal customer behavior.

Repeatable runs

Keep SQL rules organized by detection category so checks can be reviewed, changed and executed individually.

False-positive awareness

A flagged result requires investigation; thresholds, sample size and known edge cases are part of rule evaluation.

Example SQL rule pattern

This is an illustrative, simplified pattern for a weekly transaction volume check, not a transcript of a production rule or proof of a specific test result.

SELECT account_id, COUNT(*) AS recent_transactions
FROM transactions
WHERE transaction_date >= CURRENT_DATE - INTERVAL '7 days'
GROUP BY account_id
HAVING COUNT(*) > 25;
